# LCD / IFP 旧链路清理 + lcd_decision.py 瘦身计划

版本：v1.0
目标：
1. 删除已经废弃的旧 LCD / IFP 决策链路
2. 保留当前新的 LCD / IFP 完整链路，行为和入口不改变
3. 解决 lcd_decision.py 持续膨胀的问题
4. 严禁修改 LED 链路
5. 严禁因为清理旧代码导致 LCD / IFP 功能回退

==================================================
一、最高优先级约束
==================================================

【禁止修改 LED】

本次整改范围严格限制：

允许：
- LCD
- IFP
- LCD 相关旧代码清理
- lcd_decision.py 内部结构整理
- LCD/IFP 测试

禁止：
- 修改 LED Router
- 修改 LED Requirement Profile
- 修改 LED Decision
- 修改 LED Recommendation
- 修改 LED Question Flow
- 修改 LED RAG
- 修改 LED 计算逻辑
- 修改 LED 已经收紧的对话行为

如果某个共享模块同时服务 LED 和 LCD：

必须先确认调用关系。

不能因为 LCD 清理直接修改共享逻辑。

原则：

LCD/IFP 清理必须是“隔离式整改”。

==================================================
四、第二阶段：给 LCD / IFP 代码分类
==================================================

所有找到的代码必须分成 5 类。

A. 【新链路核心】

例如：

- lcd_category_understanding.py
- lcd_decision.py
- image_confirmation.py
- lcd_extractor.py
- lcd_recommendation.py
- RequirementProfile 中正在使用的 LCD 状态

这些不能删除。

也不能为了瘦身而改变业务行为。

--------------------------------

B. 【新链路辅助代码】

例如：

- LCD 字段解析
- LCD 正则
- LCD 参数提取
- IFP 特征提取
- Resolution helper
- Splicing helper
- Layout helper

只要当前新链路正在调用，就保留。

--------------------------------

C. 【旧决策代码】

重点寻找：

以前负责：

- 判断 LCD 类型
- 判断 IFP
- 决定下一问题
- 自动锁定 IFP
- 自动切换 LCD 场景
- 老的 LCD Question Planner
- 老的 IFP Policy
- 老的 LCD Policy

如果已经被新 LCD Decision Center 替代：

标记为 LEGACY。

--------------------------------

D. 【共享但仍被使用的工具】

不能直接删除。

需要确认：

是否 LED 也使用。

如果 LED 使用：

保持原样。

如果只有旧 LCD/IFP 使用：

进入后续删除候选。

--------------------------------

E. 【完全废弃代码】

满足：

1. 没有任何生产路径 import
2. 没有任何 workflow 调用
3. 没有测试依赖
4. 没有动态调用
5. 不参与状态写入
6. 不参与最终 next_action
7. 不参与 IFP lock

才允许删除。

==================================================
五、第三阶段：确认“唯一决策中心”
==================================================

这是本次整改最重要的一步。

最终必须保证：

LCD 的最终下一步只能由：

lcd_decision.py

负责。

其他模块只能：

- 提取事实
- 更新 RequirementProfile
- 提供辅助函数
- 提供 RAG 数据
- 提供产品信息

不能再决定：

- 下一问题
- LCD category
- IFP lock
- LCD branch
- 最终 next_action

禁止出现：

LCD Decision
    ↓
旧 LCD Policy
    ↓
IFP Intent
    ↓
Question Planner
    ↓
再次决定问题

这种多头决策。

最终结构：

事实提取
    ↓
RequirementProfile
    ↓
LCD Decision Center
    ↓
唯一 Next Action

==================================================
六、第四阶段：删除旧 LCD 链
==================================================

删除顺序：

第一步：

断开旧 LCD 链的调用入口。

不要先删除文件。

先让生产流程不再调用旧链。

第二步：

运行测试。

确认：

新 LCD 链仍然完整工作。

第三步：

删除旧 LCD Policy / Decision / Question Logic。

第四步：

删除只服务于旧链的 helper。

第五步：

清理 import。

第六步：

再次搜索全项目。

确保没有：

from xxx import old_lcd_policy

或者：

old_lcd_xxx()

等残留调用。

==================================================
七、第五阶段：删除旧 IFP 链
==================================================

IFP 必须特别谨慎。

IFP 是 LCD 的子系列。

最终关系必须保持：

LCD
 └── Conference / Education
       └── handwriting / interactive requirement
             └── IFP

旧 IFP 链不能继续作为独立决策中心。

重点清理：

- 老 IFP Intent Decision
- 老 IFP Policy
- 老 IFP Question Planner
- 老 IFP Category Decision
- 老 IFP 自动锁定逻辑

但是：

如果 ifp_intent.py 当前仍然承担“事实提取”功能：

不要删除。

可以保留为：

IFP Feature Extractor

例如：

客户说：

“We need handwriting.”

Extractor：

handwriting = true

然后交给：

LCD Decision Center

决定：

ifp_locked = true

也就是说：

IFP Intent 可以提取事实，

不能决定整个对话流程。

==================================================
八、IFP 判断必须统一
==================================================

最终只能由新的 LCD Decision Center 决定 IFP。

规则保持：

会议室 / 教室
≠ 自动 IFP

会议室 / 教室
    ↓
询问是否需要：
- handwriting
- whiteboard
- interactive function

如果明确需要：

→ IFP

如果明确不需要：

→ Normal LCD

如果没有回答：

→ 继续询问

不能存在：

旧 IFP Policy → IFP

新 LCD Decision → IFP

两个系统同时判断。

- 大量正则
- 参数解析
- 文本清洗
- resolution parser
- layout parser
- seam parser
- camera parser
- environment parser
- 产品数据查询
- RAG 检索
- Response 文案

==================================================
十三、lcd_decision.py 最终职责
==================================================

最终代码结构建议：

class LCDDecisionCenter:

    def decide(...):
        1. 获取当前 RequirementProfile

        2. 获取当前 branch

        3. 合并本轮新事实

        4. 检查已锁定字段

        5. 判断是否需要确认

        6. 判断当前 LCD 场景

        7. 判断 IFP gate

        8. 判断下一缺失字段

        9. 生成唯一 NextAction

        10. 写回 RequirementProfile


重点：

decide() 是唯一业务决策入口。

二十二、验收标准
==================================================

【旧链路】

必须满足：

- 旧 LCD 决策不再执行

- helper 不得产生最终 next_action
- IFP 不再存在第二套决策

【LED】

必须满足：

- 代码不修改
- 行为不改变
- 测试全部通过
- 推荐链不改变
- 对话链不改变
